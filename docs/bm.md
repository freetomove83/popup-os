# Popup OS — 비즈니스 모델 (BM)

> 운영주체: 더블엠 / 대상: 팝업을 반복 운영하는 대행사·브랜드
> 상태: **방향 확정, 가격·단위경제·법률은 초안/미확정**. (근거: `docs/landing-brief.md`, 프로젝트 메모리)

---

## 1. 한 줄 정의
팝업스토어 **구인 → 계약 → 출퇴근 → 정산**을 하나의 흐름으로 처리하는 **B2B SaaS 운영 OS**.
대행사·브랜드는 데스크톱 콘솔, 스태프는 모바일 앱으로 사용한다.

## 2. 시장 구조 — 양면(two-sided) 마켓
| 구분 | 주체 | 지불 | 역할 |
|---|---|---|---|
| 수요측(고객) | **대행사·브랜드** | **구독료** | 공고 등록·스태프 운영·정산 |
| 공급측(자산) | **스태프·프로모터** | 무료 | 검카드·지원·근무·정산 수령 |

- 성패 = 공고↔스태프 **매칭 풀의 규모** → **콜드스타트가 최대 리스크**
- 의사결정자 = 운영 매니저 / 대표

## 3. 가치 제안 & 차별점
- 핵심 가치 3: **구인·매칭 / 전자계약·출퇴근 / 정산·급여**
- 차별점 4:
  1. **실데이터 신뢰지표** — 계약+출퇴근 로그 기반(자기신고 아님), 표본수 공개
  2. **커리어 타임라인** — 스태프가 우리 행사 밖 경력까지 쌓는 **워커 소유 이력**
  3. **대행 등록** — 주관사 동의만 받으면 공고를 대신 등록(초기 구인 풀 확보)
  4. **연락처 마스킹·사진 검수** — 개인정보·신뢰 안전장치 내장

## 4. 수익 모델 (Revenue)
- **SaaS 월 구독** (핵심): 플랜별 **동시 프로젝트 수 · 스태프 수 · 기능 게이팅**
- **지급 대행**(Agency 플랜): 정산 지급 대행 — 부가 수익원(수수료/마진 구조는 미정)
- (검토) 연간 결제 시 2개월 할인
- **⭐ 알선 수수료 없음**: 채용 알선 수수료를 받지 않고 "도구 제공자" 포지션
  → **유료직업소개사업 등록 리스크 회피** (실제 운영형태는 법률 전문가 최종 확인 필요)

## 5. 요금제 (공개, 가격은 초안)
| 플랜 | 월 | 대상 | 포함 |
|---|---|---|---|
| **Lite** | ₩99,000 | 소규모 대행사·단일 브랜드 | 동시 프로젝트 1개 · 스태프 50명 · 전자계약 · QR 출퇴근 · 기본 정산 |
| **Pro** ⭐ | ₩290,000 | 성장하는 대행사 | 동시 프로젝트 5개 · 스태프 300명 · 정산 자동화 · 커리어 타임라인 · 대행 등록 |
| **Agency** | 별도 문의 | 다수 클라이언트 운영 | 무제한 프로젝트 · 다중 워크스페이스 · **지급 대행** · 전담 지원 |

공통: 언제든 해지 · 부가세 별도 · 세금계산서 발행

## 6. 전환 퍼널
- **1순위: 도입 문의** (세일즈 리드) / **2순위: 무료 시작** (14일 무료 체험, 카드 없이)
- 랜딩(`/landing`)이 퍼널 입구: 요금제 공개 + 도입 문의 폼

## 7. GTM — 초기 유입 (supply-first 시딩)
- 더블엠이 직접 대행사·브랜드에 컨택 → **동의 기반 대행 등록**으로 **공고(공급)를 먼저** 채움
- **내부 dogfooding**: 더블엠 자체 행사에 먼저 사용 (콜드스타트 완화 + 레퍼런스)
- **B2B 유입 루프**: 스태프가 커리어 타임라인에 타 주관 이력 입력 → **주관사 확인 초대** → 주관사 유입
- **성립조건 3**: ① 실제 채용 연결 ② 주관사 동의 기반(무단 수집 금지) ③ 계약·정산 주체 = 주관사

## 8. 해자(Moat)
- 실데이터 신뢰지표(로그 기반) — 모방 난이도
- 커리어 타임라인 = **워커 락인** + 타 주관사 유입 루프
- 대행 등록으로 확보한 초기 공급

## 9. 단위경제성 (미정 — 프레임)
- 목표 지표: **CAC / LTV / 페이백 기간 / 순수익 유지율(NDR)**
- 구조상 LTV는 플랜 업그레이드(프로젝트·스태프 수 증가)와 지급 대행 마진에서 발생
- 스태프측 CAC는 랜딩·커리어 타임라인 바이럴로 낮게 유지하는 설계

## 10. 리스크 & 제약
- **콜드스타트**(양면) → dogfooding + 대행 등록으로 완화
- **법규**: 유료직업소개/근로 파견 등 → 수수료 없는 SaaS 구조로 회피, 전문가 확인
- **개인정보**: 연락처 마스킹·사진 검수로 내장
- **⭐ 채널 갈등/중개 리스크** → §11

## 11. ⭐ 채널 갈등 & 중개 리스크 (핵심 고민)

### 문제 정의
Popup OS의 운영주체 **더블엠도 대행사**다. 그래서 두 가지 이해상충이 생긴다.
1. **타 대행사의 신뢰 문제** — 경쟁 대행사가 자기 운영 데이터를 "경쟁자"의 플랫폼에 넣지 않으려 함.
2. **브랜드의 디스인터미디에이션** — 브랜드가 플랫폼 존재를 알면 **대행사를 건너뛰고 직접** 스태프를 구할 수 있음 → 대행사 영역 축소.

### 왜 위험한가
- 이 리스크는 **대행사가 곧 고객**인 B2B SaaS에서 치명적이다. "경쟁자의 무기"로 인식되면 도입 자체가 막힌다.
- 실제로 이 카테고리에서 **대행사를 직접 대체하는 플랫폼**(온디맨드 스태핑 마켓플레이스)이 이미 존재한다 → §12-D.

### 완화 전략 (택1이 아니라 조합)
1. **법인·브랜드 분리** — Popup OS를 더블엠 에이전시와 **별도 법인/브랜드**로. 에이전시는 "첫 고객"일 뿐.
2. **중립성 보장(데이터 방화벽)** — 고객 데이터로 경쟁/영업하지 않음. 대행사↔브랜드↔스태프 데이터 격리, 계약상 명문화.
3. **수요 관계는 대행사 소유(BYO-brand)** — 플랫폼은 브랜드와 직접 거래하지 않고, 대행사가 브랜드를 초대하는 구조. **브랜드 직거래 마켓을 만들지 않는다**.
4. **데이터 소유권·이식성** — 대행사가 자기 데이터를 소유, 언제든 내보내기. 데이터 인질극 금지(락인은 기능으로).
5. **수익 위치** — 노동 아비트라지가 아니라 **도구/정산/지급 대행**에서 수익. "스태프를 파는 회사"가 아님을 일관되게.
6. **업계 거버넌스** — 대행사 자문위원회, (선택) 지분/코업 참여.
7. **포지셔닝 메시지** — "대행사를 대체하는 플랫폼"이 아니라 **"대행사를 위한 운영 OS"**(enabler).

> 핵심 판단: **수요측(브랜드)을 직접 소유하는 순간 §11-2가 현실화**된다. 그 유혹을 구조적으로 차단하는 설계가 방어선이다.

## 12. ⭐ 유사 비즈니스 벤치마크

### A. 한 카테고리 전체를 하나의 OS로 (Vertical OS / Vertical SaaS)
| 기업 | 카테고리 | 확장 방식 |
|---|---|---|
| **Toast** | 요식업 | POS → 결제·페이롤·주방·팀관리로 확장, "레스토랑 OS" |
| **ServiceTitan** | 홈서비스(HVAC·배관 등) | 스케줄·견적·결제·페이롤 스택 |
| **Procore** | 건설 | 현장·문서·안전·재무 통합 |
| **Mindbody** | 피트니스·뷰티 | 예약·회원·결제 |
| **Clio** | 법무 | 사건·문서·결제 |
| **Jobber / Housecall Pro** | 소규모 현장 서비스 | 운영 OS |
| **Shopify** | 소매·커머스 | 스토어 OS + 결제·물류 |
| **Veeva** | 제약 | 업종 특화 CRM → Vault |
| **Cvent** | 이벤트 | 등록·장소·마케팅 |

**공통 패턴**: 한 워크플로우를 장악 → **결제·페이롤 등 머니 플로우를 얹어** 카테고리 점유율을 크게 가져감.
→ Popup OS의 "정산·지급 대행"이 이 패턴의 핵심 축.

### B. 창업자가 그 업종의 플레이어였던 경우 (운영자=업계인)
- **Shopify** — Tobi Lütke가 **눈보드 쇼핑몰(Snowdevil)**을 운영하다 직접 만든 도구를 개방 → 업계 전체 OS로.
- **Procore** — 건설업 종사자가 만든 건설 OS.
- **Toast** — 요식업 배경 창업.
- **Buildertrend** — 주택건설업자가 만든 건설 관리 SaaS.
- **Veeva** — 제약업 경력자가 만든 제약 CRM.
> 교훈: **"업계 사람이 만든 도구"가 오히려 신뢰를 얻는다.** 단, 이후 **중립성을 증명(분리/보장)**해야 확장된다.

### C. 운영자가 이용자와 경쟁하는 사례 (이해상충의 실제 결과)
- **Amazon** — 플랫폼이면서 자체 PB(Amazon Basics)로 셀러와 경쟁 → 셀러 불만의 원형.
- **DoorDash** — 배달 플랫폼이 자체 편의점 **DashMart**로 입점 식당과 경쟁.
- **Zillow Offers** — 중개 플랫폼이 직접 매입(iBuying)에 뛰어들어 **중개인과 충돌** → 결국 **철수**.
- **Apple/Google 앱스토어** — 자사 서비스와 서드파티 앱 경쟁 논란.
> 교훈: **이해상충을 방치하면 신뢰·생태계가 무너진다.** Zillow는 리스크를 인정하고 접었다.

### D. ⭐ 대행사를 직접 대체하는 사례 (Popup OS의 진짜 위협)
- **온디맨드 스태핑 마켓플레이스**: **Instawork, Wonolo, Qwick, Veryable, Traba**
  - 기업과 워커를 **직결** → 스태핑·인력 대행사를 **디스인터미디에이션**.
  - 대상 업종: 요식·호스피탈리티·물류·이벤트·케이터링.
> 이들이 바로 "대행사 입장 영역을 줄이는" 모델. Popup OS가 **수요측을 직접 잡으면** 같은 위협이 된다.

### E. 대행사를 "고객"으로 삼는 픽앤셔블 (Popup OS가 지향할 쪽)
- **Bullhorn, Avionté, TempWorks, TargetRecruit** — 스태핑 에이전시용 ATS/CRM/페이롤.
  - 에이전시와 **경쟁하지 않고** 도구·결제로 수익. 에이전시가 곧 고객.
> 교훈: **에이전시를 고객으로 두는 "픽앤셔블" 포지션이 §11 리스크를 가장 잘 통제**한다.

### F. 최근 트렌드 (2025–2026)
- **Vertical AI Agent** — 업종 특화 AI 에이전트가 수직 SaaS를 확장/대체하는 흐름.
  → Popup OS도 "기록 시스템(OS) + AI 운영 보조(스케줄·매칭·정산 검증)"로 진화 여지.

## 14. 결론 (권고)
1. **포지션 = "대행사를 위한 OS"(enabler), 수요측(브랜드) 직접 소유 금지.**
2. **법인/브랜드 분리 + 데이터 방화벽 + 중립성 계약**으로 §11을 구조적으로 차단.
3. **수익은 도구·정산·지급 대행**(머니 플로우)에서, 노동 아비트라지 금지.
4. **초기엔 더블엠 dogfooding + 대행 등록 시딩**으로 공급 확보, 레퍼런스로 타 대행사 확장.
